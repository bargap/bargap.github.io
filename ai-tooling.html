AI Tooling

Since December 2025 I've been building my own AI tooling into how I run research, testing it on live client projects as I go. Nobody asked me to. No timeline or quality bar was allowed to slip, and only what held up on a real project stayed.

Building blocks

Code, model, me

Every tool splits the work three ways, each part used only for what it does best.

Code
Anything with a right answer

Reading documents, comparing versions, checking survey logic, running every path a respondent could take. Code gives the same result every time and costs almost nothing to rerun.

Model
Anything that takes judgment

Whether a question suits its audience, whether a finding is stated clearly, whether two differently worded rules mean the same thing. The model works from what code has already pulled out.

Me
Every call that matters

The model reviews or does the legwork, and I decide what to act on. Nothing reaches a client without my sign-off.

Philosophy

Get code to 90%, add judgment, keep learning

Getting code to handle every case perfectly is close to impossible: real documents are messy, and chasing the last few cases means an ever-growing pile of brittle rules. Getting code to about 90% is very doable. A model, briefed with what I know about how the work is done, covers the last 10% and double-checks the calls that matter most. That leaves me with only the decisions that need my judgment. And the 90% keeps growing: each project leaves the tools a little better than it found them.

Patterns

Patterns that carried over

I built and refined these tools one stage at a time, across the whole project lifecycle. Again and again, an improvement in one place turned out to be a pattern that worked elsewhere too. A few examples:

  1. Read, then check the reading
    Code→Model

    Code reads the document, and a model checks that reading against the original before anything relies on it. A bad reading makes every later check wrong.

    Steps 01–02 ↓
  2. The funnel
    Code→Model→Me

    Code flags everything, a model says which flags are real and why, and I see only what's left.

    Steps 04–06 ↓
  3. The learning loop
    Model→Me→Code

    When something goes wrong, the model or I write it down. Once the same kind of problem shows up again, I write a test for it and change the tool so it's caught automatically from then on. The survey's self-check came out of this loop.

Example

Checking a programmed survey against its design

Before a survey goes to the client or into the field, the programmed version has to match the approved questionnaire exactly: every question, answer option, skip rule, and quota. The usual way to check is to put the Word document and the survey platform side by side and scroll through both. That takes one to two hours depending on the survey, and it's easy to miss a detail deep in a long one.

The questionnaire
What the survey is supposed to do
  1. 01Code
    Read the Word document

    Code turns the questionnaire into structured data: questions, options, logic notes, quotas.

  2. 02Model
    Check the reading

    Word documents are messy, so a model checks code's reading against the original and fixes what it got wrong, like a programming note that ended up inside an answer option or a grid whose rows shifted. A bad reading produces mostly false alarms later, so this has to finish first.

The programmed survey
What the survey actually does
  1. 03Code
    Read and check the survey export

    The survey platform exports a structured file, so code reads it directly, with no model involved. Before any comparison, code also checks the survey against itself: whether every rule points at a question and answer that exist, whether quotas are tied to live questions, whether every value the survey reads is set somewhere. Each of those checks exists because that mistake once got through. Then it runs every combination of screener answers and reports who gets through. A comparison can't catch a mistake both documents share, so this has to happen on its own.

Compare and decide
Where the two disagree, and what to do about it
  1. 04Code
    Line them up

    Code matches every question and option across the two readings and lists the differences. Some are certain, like a missing question or a wrong number of options. Others need judgment, like slightly different wording or logic written as prose in one and as a rule in the other.

  2. 05Model
    Sort real problems from noise

    A model works through the uncertain differences and separates real errors from harmless ones, with a reason for each. On one real survey, all 15 serious-looking flags turned out to be harmless, and three small real errors surfaced underneath them.

  3. 06Me
    Decide

    I get a short checklist of real issues, each with the fix already written. I tick what to fix, or add a note to push back or redirect, and the analyst gets the result. Anything the tools couldn't confirm is listed separately.
